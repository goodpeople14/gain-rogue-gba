# 개발 저널 001: AI와 함께 프로젝트의 기억을 저장소로 옮기기

- 날짜: 2026-08-10
- 성격: 사고 과정 기록 / 향후 책 집필 원재료

이 저널은 작업 목록을 반복하지 않는다. Git이 기록하기 어려운 생각의 변화, 예상 밖의 발견, 선택과 이유, 배운 원칙을 남긴다.

## 1. 처음 생각했던 것

GPT에게 먼저 작업 지시서를 작성하게 하고, 지시서의 요약과 내가 꼭 알아야 할 내용을 확인한 다음 Codex에게 실제 구현을 맡기는 방식을 사용해 왔다.

이 과정은 자연스럽게 다음 역할 분담이 되었다.

```text
GPT/제시: 구조와 의도를 정리하고 작업 지시서를 설계
사용자: 지시서와 중요한 판단을 검수하고 승인
Codex: 실제 저장소를 읽고 구현
```

처음에는 GPT가 프로젝트의 주요 모듈과 과거 대화 맥락을 알고 있으므로 이 기억을 계속 활용하면 된다고 생각했다.

또 Repository에 저널을 하나 두면 GPT가 프로젝트를 더 잘 기억하는 데 도움이 되지 않을까 하는 생각에서 문서화를 검토하기 시작했다.

## 2. 예상과 달랐던 것

Claude와 GPT의 논의를 거치면서 저널의 목적이 특정 AI의 기억을 보조하는 것보다 더 크다는 점이 드러났다.

채팅 히스토리나 모델의 기억에 프로젝트 맥락을 맡기면 도구를 바꾸거나 세션이 사라졌을 때 설계 이유가 함께 사라질 수 있다.

반대로 중요한 판단을 Repository에 남기면 GPT, Codex, Claude 또는 미래의 다른 도구가 같은 기록을 다시 읽을 수 있다.

즉 문서화의 핵심은 특정 AI를 더 강하게 만드는 것이 아니라 프로젝트 기억을 특정 AI에게서 분리해 프로젝트 자체의 자산으로 만드는 것이었다.

또 처음에는 개발 효율만 생각하면 작업 일지를 Git과 중복해서 남길 필요가 없다는 의견이 설득력 있었다. 하지만 이 프로젝트는 게임 완성뿐 아니라 개발 경험을 나중에 책으로 정리해 보는 목적도 있다.

그 목적까지 포함하면 "처음에는 왜 그렇게 생각했는지", "무엇을 만나 생각이 바뀌었는지"는 Git commit만으로 복원하기 어렵다. 나중에 회상해서 쓰면 실제 좌충우돌 과정이 지나치게 매끄럽게 재구성될 가능성도 있다.

## 3. 내린 판단과 이유

프로젝트 기억을 다음처럼 분리한다.

- 코드: 현재 프로그램이 실제로 어떻게 동작하는지 보여 주는 1차 근거
- Git: 무엇이 변경되었는지 기록
- `AGENTS.md`: AI가 어떻게 작업해야 하는지 규정
- `docs/architecture.md`: 현재 구조를 빠르게 찾기 위한 얇은 지도
- `docs/decisions/`: 중요한 결정과 그 이유
- `docs/journal/`: 생각의 변화, 실패, 예상 밖의 발견과 배운 점

저널은 매일 쓰지 않는다. 다음 중 의미 있는 사건이 있을 때만 작성한다.

1. 처음 생각과 실제 결과가 달랐을 때
2. 중요한 설계 선택을 했거나 기존 생각을 바꿨을 때
3. 실패나 시행착오에서 일반화할 수 있는 교훈을 얻었을 때
4. 향후 책에서 개발 과정 자체를 설명할 가치가 있을 때

저널 초안은 가능한 한 해당 세션의 AI가 작성한다. 사용자는 작성 노동을 떠안기보다 내용을 수정하고 승인하는 편집자이자 최종 결정자 역할을 맡는다.

저널 전체를 모든 작업의 기본 컨텍스트로 밀어 넣지 않는다. 평소에는 `AGENTS.md`와 필요한 현재 문서만 읽고, 과거 판단의 이유가 필요하거나 기존 결정과 충돌하거나 책의 재료를 찾을 때 관련 저널만 선택적으로 읽는다.

## 4. 같은 날 이어진 게임 구조 고민: 충돌을 더 크게 보기 시작하다

고블린을 여러 마리 배치하고 공격·피격·물리 충돌을 다루면서 기존 충돌 구조를 단순한 "부딪혔는가"보다 역할별로 생각하게 되었다.

현재 프로젝트에는 이미 다음 구분이 있다.

- `Hitbox`: 공격을 전달한다.
- `Hurtbox`: 공격을 받을 수 있다.
- `Pushbox`: 물리적 겹침을 막는다.

여기서 처음에는 히트맵 또는 충돌 타입의 종류를 늘려 무적, 슈퍼아머 같은 상태까지 함께 표현하면 계산이 편할 수 있다고 생각했다.

하지만 논의를 진행하면서 공간 판정과 캐릭터 상태는 다른 책임이라는 쪽으로 생각이 바뀌었다.

무적이나 슈퍼아머는 "이 공간이 무엇인가"가 아니라 "현재 이 캐릭터가 어떤 상태인가"에 가깝다. 따라서 충돌 종류를 늘리는 대신 캐릭터/게임 상태로 두는 방향이 더 자연스럽다고 판단했다.

이 생각은 한 단계 더 확장되었다.

공간을 담당하는 시스템이 있다면 그 시스템은 위치와 주변 후보를 제공하는 데 집중하고, "이 접촉이 피해인가, 회복인가, 트리거인가" 같은 의미 해석과 상태 변경까지 모두 소유하지 않는 편이 책임 분리에 유리하다.

아직 현재 코드에 `Spatial Manager`나 범용 `Effect/Trigger` 계층이 구현되어 있다고 가정하지 않는다. 실제 도입 여부와 이름은 다음 구현에서 저장소를 조사한 뒤 결정한다.

## 5. 다음 단계: 타일도 상태를 가져야 한다

맵을 만들기 시작하면 캐릭터끼리의 충돌만으로는 부족하다.

각 타일에는 최소한 "갈 수 있는 곳인가, 갈 수 없는 곳인가"라는 공간적 의미가 필요하다.

따라서 다음 개발에서는 충돌 구조 고도화와 함께 타일별 상태 구조를 검토한다.

초기에는 복잡하게 시작하지 않는다.

- 이동 가능
- 이동 불가
- 실제 게임에서 필요성이 확인된 최소한의 지형 속성

정도부터 시작한다.

GBA라는 제한된 환경을 고려하면 큰 객체 그래프나 동적 구조보다 작은 정수 또는 비트 플래그 기반의 고정 크기 표현이 적합할 가능성이 있다. 다만 이것은 아직 설계 후보이며 실제 맵 데이터 구조와 메모리 사용량을 확인한 뒤 확정한다.

중요한 경계는 유지한다.

```text
타일 상태 = 공간/지형의 성질
캐릭터 상태 = 캐릭터의 현재 게임 상태
Hitbox/Hurtbox/Pushbox = 객체 사이 공간 관계와 전투 판정의 역할
```

이 세 가지를 한 종류의 범용 상태 체계로 섞지 않는다.

## 6. 이번 과정에서 배운 원칙

### 답은 목적에 따라 달라진다

"개발 문서를 최소 비용으로 유지한다"만 목표라면 저널을 거의 쓰지 않는 것이 효율적일 수 있다.

하지만 "게임을 만들면서 배운 과정을 나중에 책으로 남긴다"까지 목표에 포함하면 사고 과정은 보존해야 할 데이터가 된다.

좋은 구조는 기능만 보고 정하는 것이 아니라 프로젝트의 최종 목적까지 보고 정해야 한다.

### 코드는 사실이고 문서는 주장이다

AI가 작성한 문서가 매끄럽다고 해서 실제 코드가 그대로 구현되어 있다는 뜻은 아니다.

문서와 코드가 충돌하면 코드를 먼저 확인한다. 문서는 설계 의도와 과거 판단을 이해하기 위한 근거이지 현재 실행 상태를 대신하지 않는다.

### AI가 작성하고 사람이 승인한다

문서 갱신을 별도 숙제로 만들면 오래 유지하기 어렵다.

설계 → 구현 → 검증의 작업 루프에 문서 갱신을 포함하고 AI가 초안을 만들도록 한다. 사용자는 중요한 결정과 기록을 검수하고 승인한다.

### 프로젝트의 기억은 프로젝트가 소유해야 한다

특정 GPT 세션, 특정 Codex 세션, 특정 Claude 대화가 프로젝트의 유일한 기억 저장소가 되어서는 안 된다.

AI는 교체될 수 있지만 Repository의 코드와 결정, 저널은 남는다.

## 7. 다음에 확인할 질문

- 현재 이동/충돌 코드에서 캐릭터 대 캐릭터 충돌 후보는 누가 찾고 있는가?
- 맵 타일 충돌을 기존 `Pushbox` 흐름과 어디까지 공유할 수 있는가?
- 타일 상태를 몇 비트로 표현하면 현재 목표에 충분한가?
- 이동 가능/불가 외에 첫 맵에서 실제로 필요한 타일 속성이 있는가?
- 충돌 후보 탐색을 공통화할 시점이 실제로 왔는가, 아니면 현재 구조로 한 단계 더 진행하는 편이 단순한가?
- Effect/Trigger라는 별도 계층이 실제 요구에서 필요해지는가?

이 질문들은 구현을 미리 확정하기 위한 것이 아니라 다음 설계에서 실제 코드를 보고 판단하기 위한 체크포인트다.
