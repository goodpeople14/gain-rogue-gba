# 개발 저널 002: 현재 구조는 왜 이렇게 되었고, 어디까지 확장할 것인가

- 날짜: 2026-08-10
- 성격: 구조 형성 과정 복원 / Blue-Red 검토 / 향후 책 집필 원재료

이 문서는 현재 구조를 정당화하기 위해 쓰지 않는다. Git, Issue, 코드와 기존 문서에서 확인되는 근거를 바탕으로 프로젝트 구조가 어떻게 만들어졌는지 복원하고, 지금 시점에서 다시 평가한다.

## 1. 확인된 사실

### 단순 공격에서 역할 분리로 발전했다

Git 이력을 보면 구조는 처음부터 큰 게임 아키텍처를 설계한 뒤 구현한 것이 아니었다.

- `940aec5` — 검사 공격과 리스폰 허수아비 추가
- `734b76f` — 8방향 참격 시각 효과 추가
- `d99f15b` — Pushbox 이동 충돌, 프레임 기반 Melee Hitbox, 공격별 피격 기록 추가 및 소스 책임 재정리
- `672eed0` — 검사 고유 행동을 `Character`에서 분리하고 `Swordsman`이 소유하도록 변경

즉 공격을 먼저 만들고, 실제 충돌·중복 적중·캐릭터별 행동 문제가 나타나면서 책임이 분리되었다.

현재 전투 문서는 `Hitbox`, `Hurtbox`, `Pushbox`를 서로 다른 의미로 정의하고 있으며 캐릭터 상태를 충돌 영역 종류로 표현하지 않는다고 명시한다.

### 적이 추가되면서 현재 구조가 실제로 확장되었다

- `6aa8cb6` — 근접 고블린 프로토타입 추가
- `e73d8cc` — 고블린 공격 Commit과 실제 Hitbox 정합성 수정
- `c067290` — 안전한 고블린 리스폰 추가
- PR #33 / Issue #23 — 다수 고블린이 각자 상태, 대상 ID, 공격 기록, Pushbox를 갖도록 확장
- `3bd0c2d`, `fd9f282` — 다중 고블린 상호 충돌에서 발생한 막힘과 회피 문제 수정
- `95ea10e` — 석궁 고블린과 원거리 공격 추가

Issue #23은 범용 EnemyManager, ECS, 길 찾기, 군집 이동, 공격 스케줄러를 이번 범위에서 명시적으로 도입하지 않았다고 기록한다.

이 점은 현재 구조가 미래 기능을 예상해 큰 프레임워크를 먼저 만든 것이 아니라 실제 요구가 생긴 만큼 확장되어 왔음을 보여 준다.

### 현재 `GameScene`은 조정자이지만 책임 집중이 시작되고 있다

현재 `GameScene`은 다음 객체를 직접 소유한다.

- 플레이어와 `PlayerController`
- 근접 고블린 4마리
- 석궁 고블린 1마리
- 석궁 투사체 Pool
- Hit Effect Manager
- Collision Debug Overlay
- Battlefield

또한 플레이어 이동 시 활성 적 Pushbox 목록을 수집하고, 각 근접 고블린과 석궁 고블린을 위한 장애물 목록을 별도로 만든다.

전투 업데이트에서도 각 적의 공격/피격 해석을 순회하며 조정한다.

따라서 `GameScene`은 아직 개별 전투 로직을 직접 구현하는 클래스는 아니지만, 객체 종류가 늘수록 "누가 누구와 상호작용하는가"를 조립하는 책임이 빠르게 늘어나는 위치에 있다.

### 현재 맵은 아직 타일 상태 시스템이 아니다

`Battlefield`는 현재 화면 크기와 UI 폭으로부터 이동 가능 사각 경계를 계산한다. 이동 해결 함수는 Pushbox 장애물 목록과 `MovementBounds`를 입력받는다.

즉 현재 이동 충돌은 다음 두 종류로 구성된다.

1. 사각형 전장 경계
2. 객체 Pushbox 목록

타일별 이동 가능/불가, 지형 타입, 타일 효과를 표현하는 데이터 구조는 현재 확인되지 않는다.

Issue #37에서는 화면보다 큰 맵과 Camera를 도입하되 World 좌표와 화면 좌표를 분리하고, 범용 World Framework나 Chunk Streaming을 미리 만들지 않는 방향을 이미 잡고 있다.

## 2. 대화 기반 설계 맥락

아래 내용은 코드에 이미 구현된 사실이 아니라 설계 대화에서 나온 방향이다.

- Spatial 역할이 필요해질 경우 위치와 주변 후보 제공에 집중시킨다.
- 접촉의 의미 해석과 상태 변경까지 Spatial에 넣지 않는다.
- 무적, 슈퍼아머 같은 캐릭터 상태를 HitMap/Collision 종류로 표현하지 않는다.
- 맵 개발 시 타일에는 최소한 이동 가능/불가 같은 공간 상태가 필요하다.
- Spatial Manager나 범용 Effect/Trigger라는 이름과 계층은 실제 필요가 확인된 뒤 도입한다.

이 대화 맥락은 현재 코드의 사실과 구분해서 유지한다.

## 3. Blue Team: 현재 구조를 유지해야 하는 가장 강한 논거

### Hitbox / Hurtbox / Pushbox 분리는 실제 문제에서 나온 구조다

세 영역은 이름만 다른 추상화가 아니다.

- 공격이 닿는가
- 공격을 받을 수 있는가
- 물리적으로 겹칠 수 있는가

라는 서로 다른 질문을 해결한다.

고블린 공격 정합성 문제에서도 공격 시작 판단과 실제 Hurtbox 판정 기준이 달라 빗나가는 문제가 실제로 발생했다. 역할이 분리되어 있었기 때문에 어떤 기준이 어긋났는지를 진단할 수 있었다.

따라서 이 구분을 다시 하나의 범용 Collision 타입으로 합치는 것은 단순화가 아니라 정보 손실에 가깝다.

### 구조가 실제 요구를 따라 점진적으로 커졌다

`Character`에 검사 공격을 계속 넣지 않고 `Swordsman`으로 옮긴 변경, 다중 고블린에서도 EnemyManager/ECS를 만들지 않은 선택은 현재 프로젝트가 비교적 보수적으로 추상화를 도입하고 있다는 근거다.

GBA에서는 작은 고정 배열과 명시적 반복이 현대 엔진식 동적 구조보다 오히려 예측 가능하고 디버깅하기 쉽다.

### 지금 구조로 적 종류가 하나 더 추가되는 것까지는 버틸 수 있음이 확인되었다

근접 고블린에서 석궁 고블린까지 확장했지만 기존 Hit/Hurt/Push 의미를 버리지 않고 원거리 공격을 추가했다.

즉 현재 전투 핵심 경계는 적어도 두 종류의 공격 방식에서 재사용되고 있다.

## 4. Red Team: 현재 구조를 공격한다면 어디가 약한가

### `GameScene`이 미래의 God Object 후보가 되고 있다

현재 `GameScene`은 적의 종류를 알고, 각 적 배열을 알고, 어떤 Pushbox가 누구를 막아야 하는지 알고, 공격과 피격 해결 순서까지 알고 있다.

적이 5종, 10종으로 늘거나 맵 장애물이 추가되면 `_active_enemy_pushboxes`, `_goblin_blocking_pushboxes`, `_crossbow_blocking_pushboxes`와 유사한 조립 코드가 늘어날 가능성이 높다.

현재는 허용 가능한 수준이지만 이 패턴이 반복되면 구조적 압력이 명확해진다.

### `max_movement_obstacles = 5`는 현재 콘텐츠 수에 강하게 결합되어 있다

`CollisionBody` 쪽의 전역 상수는 "한 이동 적이 플레이어 + 다른 4개의 적에게 막힌다"는 현재 전장 구성을 직접 반영한다.

GBA 고정 용량 정책에는 잘 맞지만, 맵 타일/장애물이 추가되면 같은 목록에 모두 넣을 것인지 별도 공간 충돌로 처리할 것인지 경계를 다시 정해야 한다.

### Spatial / Effect / Trigger를 지금 도입하면 오히려 과설계가 될 수 있다

현재 근접/원거리 전투의 상호작용은 아직 직접적이며 종류도 제한적이다.

"앞으로 필요할 것 같다"는 이유만으로 범용 Spatial Manager, Event Bus, Effect/Trigger Framework를 추가하면 실제 사용 사례보다 추상화가 먼저 생긴다.

GBA에서는 추가 간접 호출, 데이터 구조, 고정 용량 설계와 디버깅 비용도 무시할 수 없다.

### 타일 상태를 객체 상태와 같은 범용 시스템으로 만들면 책임이 다시 섞인다

타일은 공간의 속성을 나타내고 캐릭터 상태는 행위자의 상태를 나타낸다.

두 구조를 하나의 범용 State/Effect 체계로 통합하면 처음에 피하려 했던 "공간과 게임 상태의 혼합" 문제가 다시 나타날 수 있다.

## 5. 종합 판단

### A. 현재 전투/충돌 구조

**유지**

`Hitbox / Hurtbox / Pushbox` 분리는 현재 규모에서 과하지 않다. 실제 버그 분석과 근접/원거리 확장에서 값을 증명했다.

### B. 현재 구조를 유지한 충돌 고도화

**가능하며 권장**

기존 세 충돌 의미를 유지하고 맵/타일 충돌을 별도의 공간 제약으로 추가하는 것이 우선이다.

모든 충돌을 하나의 Manager에 모으는 것보다 "무엇을 조회하는가"와 "무슨 의미인가"를 구분해야 한다.

### C. Spatial Manager

**보류**

현재 바로 만들지 않는다.

다음 조건 중 둘 이상이 실제 코드에서 나타날 때 도입을 재검토한다.

- 플레이어와 여러 적이 동일한 주변 후보 수집 코드를 반복한다.
- 맵 장애물까지 포함하면서 `GameScene`의 장애물 조립 코드가 크게 늘어난다.
- 동일 공간 질의를 AI, 충돌, 공격, Trigger가 각각 반복한다.
- 전체 객체 순회 비용이 실제 성능 문제로 확인된다.

그때도 Spatial은 위치/후보 조회까지만 담당하고 상태 변경은 하지 않는 방향을 우선한다.

### D. Effect / Trigger

**보류**

현재 직접적인 공격/피격 처리만으로 충분하다.

회복 지대, 함정, 문, 스위치, 버프 타일처럼 "같은 접촉 결과가 서로 다른 게임 의미를 낳는" 실제 두 번째·세 번째 사용 사례가 생길 때 공통 계층 도입을 검토한다.

### E. 타일별 상태 구조

**고도화 대상이지만 최소 구조부터**

맵 개발에 들어가면 타일 상태는 필요하다. 다만 첫 버전은 다음 정도면 충분할 가능성이 높다.

- 이동 가능 / 이동 불가
- 필요가 확인된 소수의 지형 플래그

표현은 작은 enum 또는 bit flag와 고정 크기 데이터를 우선 검토한다.

타일 상태에는 무적, 슈퍼아머 같은 캐릭터 상태를 넣지 않는다.

### F. GBA 때문에 다르게 가져갈 부분

- 고정 용량 배열과 컴파일 타임 상한을 적극 활용한다.
- 범용 ECS/Event Bus/동적 객체 그래프를 기본값으로 삼지 않는다.
- 새로운 Manager는 이름이 예뻐서가 아니라 반복 책임 또는 성능 문제라는 실제 압력이 있을 때 만든다.
- CPU와 메모리뿐 아니라 OBJ palette처럼 GBA 고유 자원 한계도 구조적 비용으로 본다.

## 6. 지금 유지 / 고도화 / 보류할 것

### 유지

- `Character`와 구체 캐릭터 행동의 책임 분리
- `PlayerController`의 입력→명령 역할
- `Hitbox / Hurtbox / Pushbox` 의미 구분
- 시각 효과와 실제 판정 분리
- 고정 용량 컨테이너와 명시적 상한

### 고도화

- 맵이 들어올 때 타일별 이동 가능/불가 상태
- World 좌표 기반 맵/Camera 구조
- `GameScene`의 충돌 후보 조립 코드가 실제로 반복될 경우 그 책임만 최소 단위로 추출

### 보류

- 범용 Spatial Manager
- 범용 Effect/Trigger Framework
- ECS
- 범용 EnemyManager
- Path Finding / 군집 시스템

## 7. 처음 생각과 지금 판단의 차이

처음에는 객체와 적이 늘어나면 Spatial Manager와 Effect/Trigger를 별도 시스템으로 미리 나누는 것이 자연스럽다고 생각했다.

Repository를 다시 확인하니 현재 프로젝트는 이미 여러 번 "필요가 생긴 뒤 최소 구조를 분리"하는 방식으로 성공적으로 발전해 왔다.

따라서 다음 단계에서도 같은 원칙을 유지하는 편이 일관된다.

즉 좋은 구조를 미리 완성하는 것이 목표가 아니라, 현재 책임이 실제로 버티지 못하는 지점을 관찰하고 그 순간 가장 작은 분리를 적용하는 것이 목표다.

## 8. 이번 검토에서 얻은 원칙

### 추상화는 예상이 아니라 압력에서 만든다

미래에 필요할 것이라는 예상만으로 Manager를 만들지 않는다.

중복 코드, 책임 혼합, 성능 병목, 테스트 어려움처럼 현재 코드에서 관찰되는 압력이 생겼을 때 분리한다.

### 역할 분리는 클래스 수가 아니라 질문의 차이로 판단한다

Hitbox/Hurtbox/Pushbox는 클래스가 세 개라서 복잡한 것이 아니다. 각각 다른 질문에 답하기 때문에 분리할 가치가 있다.

반대로 Spatial/Effect/Trigger가 아직 같은 실제 질문을 해결하지 않는다면 지금은 클래스 이름만 늘릴 수 있다.

### GBA의 단순함은 제약이 아니라 설계 기준이다

현대 게임 엔진에서 흔한 구조가 항상 정답은 아니다. 작은 고정 배열과 직접적인 흐름이 더 예측 가능하고 안전할 수 있다.

### 다음 구조는 맵에서 시험받는다

현재 전투 구조의 다음 실제 시험대는 타일/맵/Camera다.

타일 상태와 World 좌표가 들어왔을 때 `GameScene`과 이동 충돌 코드가 얼마나 복잡해지는지 확인하면 Spatial 책임 분리의 필요성을 추측이 아니라 근거로 판단할 수 있다.
