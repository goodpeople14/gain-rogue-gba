# TDD 도입과 개발 의사결정 방식의 변화

관련 이슈: #56

## 배경

프로젝트 초기에는 다음 흐름이 중심이었다.

```text
구현
→ build
→ mGBA 실행
→ 체감 확인
→ 이상하면 수정
```

작은 기능을 빠르게 만들 때는 충분했다. 하지만 Goblin, Crossbow, SpatialManager, Stage, Floor 같은 기능이 서로 연결되기 시작하면서 수정 하나의 영향 범위를 사람이 계속 기억하고 추론해야 했다.

문제는 테스트가 없다는 사실 자체보다, **무엇을 반드시 유지해야 하는지가 코드 밖에서 명확한 계약으로 존재하지 않는 것**이었다.

## TDD 도입 전의 어려움

기능이 늘어난 뒤에는 이런 일이 반복됐다.

- 기존 동작을 다시 코드에서 확인해야 했다.
- 리팩터링할 때 어떤 행동을 지켜야 하는지 매번 추론했다.
- 수동 mGBA 검증 범위가 계속 커졌다.
- 이전에 맞았던 동작이 언제 깨졌는지 찾기 어려웠다.
- "아마 안전할 것"이라는 판단 비중이 높아졌다.

특히 AI, Collision, Spatial처럼 보이지 않는 규칙이 많아질수록 이 비용이 커졌다.

## 행동 계약을 먼저 적기 시작했다

이후에는 구현을 바로 시작하기보다 먼저 어떤 행동이 보장되어야 하는지를 정리하고 테스트로 잠그는 방식을 사용하기 시작했다.

예를 들면 다음과 같다.

- 다른 Floor의 Actor는 Pushbox obstacle에서 제외한다.
- CHASE BOX 경계에서는 HOLD한다.
- FLEE BOX 내부에서는 RETREAT한다.
- 짧은 block만으로 local detour를 시작하지 않는다.
- 직접 경로가 다시 열리면 detour를 종료한다.
- Spatial full scan과 local cell query는 같은 후보 결과를 반환해야 한다.

이렇게 하면 내부 구현은 바뀌어도 외부 행동 계약은 유지할 수 있다.

## 의사결정 방식이 어떻게 바뀌었나

도입 전에는 구조 변경을 할 때 코드를 다시 읽고 영향 범위를 예상하는 비중이 컸다.

```text
도입 전
코드 확인
→ 영향 추측
→ 수정
→ mGBA에서 문제 찾기
```

TDD를 적용한 뒤에는 다음처럼 판단할 수 있게 되었다.

```text
행동 계약 확인
→ 바꿔도 되는 부분과 유지해야 하는 부분 구분
→ 구현 변경
→ 자동 회귀 검증
→ mGBA에서 체감 확인
```

이 차이는 리팩터링, AI 단순화, Spatial 최적화, Floor 규칙 추가 같은 작업에서 특히 컸다.

## TDD가 실제로 도움이 된 영역

### 리팩터링

공통 이동 코드를 추출할 때 기존 Melee 행동을 테스트로 잠그면 "공통화 후에도 이전 행동이 같은가"를 확인할 수 있다.

### AI 단순화

원거리 AI에서 최적 사격 위치 탐색을 제거해도 SEARCH / APPROACH / HOLD / RETREAT 계약이 유지되는지를 볼 수 있다.

### Spatial 최적화

Stage 전체 cell scan을 local cell query로 바꾸더라도 반환 후보 집합이 동일한지를 비교할 수 있다.

### Floor 규칙

GROUND / UPPER를 추가할 때 same-floor Push와 cross-floor 제외 규칙을 명시적으로 검증할 수 있다.

## 중요한 오해: TDD는 RED를 만드는 놀이가 아니다

프로젝트를 진행하면서 이미 코드가 만족하고 있는 조건에 대해 억지로 실패 테스트를 만들려는 순간도 있었다.

하지만 목적은 "반드시 RED부터 본다"가 아니다.

> TDD의 목적은 아직 보장되지 않은 행동을 명확한 계약으로 만드는 것이다.

이미 현재 코드가 계약을 만족한다면 characterization test로 현재 동작을 잠그고 다음 변경의 회귀 기준으로 사용할 수 있다.

## TDD가 대신하지 못하는 것

게임에서는 테스트만으로 결정할 수 없는 것이 많다.

- 공격 템포가 재미있는가
- 적의 압박감이 적당한가
- TELEGRAPH가 너무 긴가
- CHASE / FLEE 거리가 자연스러운가
- 이동이 답답하게 느껴지지 않는가
- 이펙트와 화면 가독성이 좋은가

이런 것은 실제 플레이가 필요하다.

그래서 이 프로젝트에서 TDD와 mGBA는 경쟁 관계가 아니다.

```text
TDD / 자동 테스트
→ 논리적 계약과 회귀 검증

build
→ 기술적 정상성 검증

mGBA
→ 실제 플레이와 시각적 체감 검증

사용자 승인
→ 완료 판단
```

각 단계의 역할이 다르다.

## 개발 방식에서 얻은 변화

TDD를 적용하면서 가장 크게 바뀐 점은 테스트 개수보다 **질문의 형태**였다.

이전에는:

> 이 코드를 이렇게 바꿔도 될까?

라고 물었다면, 이후에는:

> 이 변경 후에도 어떤 행동은 반드시 같아야 하고, 어떤 행동은 바뀌어야 하는가?

를 먼저 생각하게 되었다.

이렇게 행동을 먼저 정의하면 Codex에게 작업을 맡길 때도 구현 방법보다 완료 조건을 더 명확하게 전달할 수 있다.

## 앞으로 유지할 원칙

1. 기능 구현 전 핵심 행동 계약을 먼저 적는다.
2. 이미 맞는 동작을 억지로 깨뜨려 RED를 만들지 않는다.
3. 리팩터링 전에는 현재 정상 행동을 characterization test로 잠근다.
4. 자동 테스트가 통과해도 게임의 재미와 시각적 품질은 mGBA에서 확인한다.
5. build 성공과 gameplay 성공을 같은 의미로 취급하지 않는다.
6. 최종 완료는 자동 검증과 실제 ROM 확인을 함께 본다.

> 테스트는 게임을 대신 플레이해 주는 도구가 아니라, 우리가 이미 맞다고 결정한 규칙을 다시 잃지 않게 해주는 장치다.
