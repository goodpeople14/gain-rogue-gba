# Stage1 바위 충돌 문제에서 배운 것

## 배경

Stage1 배경과 SpatialManager를 연결한 뒤, 중앙 바위 주변을 이동할 때 캐릭터가 모서리에 과하게 걸리고 보이는 바위보다 더 큰 벽에 부딪히는 듯한 느낌이 나타났다.

처음에는 StageData의 8×8 cell 단위 BLOCKED만으로도 장애물을 표현할 수 있다고 생각했다. 실제로 Stage 경계나 큰 벽처럼 셀 단위로 끊어도 자연스러운 구조에는 이 방식이 잘 맞았다.

하지만 작은 바위처럼 시각적 외곽과 실제 충돌 영역이 다르게 느껴져야 하는 오브젝트에는 같은 방식이 어울리지 않았다.

## 처음 생각과 실제 결과

초기 바위는 StageData 내부의 2×2 BLOCKED 영역으로 표현했다.

논리적으로는 단순했다.

```text
StageData BLOCKED
→ 이동 불가
```

하지만 8×8 cell 네 칸은 16×16의 완전한 사각형이 된다. 둥근 바위 이미지를 사각형 셀로 막으니 캐릭터는 바위의 빈 모서리에서도 충돌했고, 화면에서는 아직 여유가 있어 보이는데 이동이 막혔다.

문제는 충돌 계산 자체가 틀렸다기보다 **시각적 크기와 물리적 점유 영역을 같은 것으로 취급한 설계**였다.

## 첫 번째 전환: StageData와 개별 장애물의 책임 분리

바위를 StageData의 BLOCKED에서 제거하고 Static Obstacle `WorldBox`로 분리했다.

이 과정에서 장애물의 역할을 다음처럼 구분하게 되었다.

```text
StageData BLOCKED
→ 전장 경계, 벽, 큰 구조물처럼 grid 단위로 막아도 자연스러운 영역

Static Obstacle
→ 바위, 상자, 기둥처럼 보이는 크기와 실제 충돌 크기를 독립적으로 조정해야 하는 오브젝트
```

이 결정으로 바위 이미지는 16×16이어도 실제 충돌 영역은 그보다 작게 둘 수 있게 되었다.

여기서 얻은 첫 번째 원칙은 다음과 같다.

> **Visual footprint와 Collision footprint는 같을 필요가 없다.**

## 두 번째 문제: 모서리에서의 이동 처리

충돌 영역을 줄인 뒤에도 대각선으로 바위 모서리를 스칠 때 움직임이 기계적으로 느껴졌다.

조사해 보니 기존 movement resolver는 대각선 충돌 시 항상 X축을 먼저 처리하고 있었다. 그래서 세로 이동량이 더 큰 상황에서도 작은 X 이동을 보존하고 더 큰 Y 이동을 버리는 경우가 있었다.

예를 들어 원하는 이동이 다음과 같을 때:

```text
x = +0.5
y = +1.0
```

세로 이동이 더 강한데도 X축을 먼저 살리는 결과가 나올 수 있었다.

TDD로 이 상황을 재현한 뒤 resolver를 다음 규칙으로 변경했다.

```text
|dy| > |dx|  → Y 우선
그 외        → X 우선
동률         → 기존 X 우선 규칙 유지
```

그 결과 장애물에 닿은 이후에도 입력의 주 방향을 유지하며 자연스럽게 미끄러지는 `dominant-axis slide`가 만들어졌다.

여기서 두 번째 원칙을 구분할 수 있었다.

```text
Collision footprint
→ 언제 충돌을 시작하는가

dominant-axis slide
→ 충돌한 뒤 어떤 이동을 보존하는가
```

둘은 같은 문제가 아니었다.

## TDD가 실제로 도움이 된 지점

이번 문제에서 TDD는 단순히 테스트 수를 늘리는 용도가 아니었다.

사람이 느낀 "모서리에서 이상하게 걸린다"는 감각을 실행 가능한 규칙으로 바꾸는 역할을 했다.

검증한 핵심 행동은 다음과 같았다.

- 정면으로 들어가면 막힌다.
- 장애물에 평행한 이동은 유지된다.
- 네 방향 모서리에서 더 큰 입력 축을 보존한다.
- 장애물이 없으면 대각선 이동은 변하지 않는다.
- resolve 결과가 장애물과 엄격하게 겹치지 않는다.

이 경험으로 다음 흐름이 유효하다는 것을 확인했다.

```text
mGBA에서 이상한 느낌 발견
→ 재현 가능한 행동 규칙으로 번역
→ RED 테스트
→ 최소 수정으로 GREEN
→ mGBA에서 다시 체감 확인
```

자동 테스트가 플레이 감각을 대신하는 것은 아니지만, 플레이 감각에서 발견한 문제를 다시 깨지지 않는 계약으로 바꾸는 데 유용했다.

## 잘못 들어갔던 방향

문제를 해결하는 과정에서 Debug 표시와 TDD 자체가 필요 이상으로 커진 순간도 있었다.

Static Obstacle을 더 잘 보이게 하려다가 기존 Hit/Hurt/Push/Commit Debug와 겹쳐 화면이 보라색 박스로 가득 찼고, 정작 확인하려던 바위 충돌 영역을 보기 어려워졌다.

또 이미 코드가 만족하고 있는 조건에 대해 억지로 RED를 만들려는 식의 지시도 생겼다.

실제 코드는 이미:

- 바위 Visual 16×16
- Static Collision은 Visual보다 작음
- StageData의 중앙 2×2 BLOCKED 제거

상태였기 때문에, "16×16 충돌을 12×12로 바꾼다"는 전제를 강제로 적용하면 오히려 회귀를 만드는 일이었다.

여기서 중요한 교훈을 얻었다.

> **TDD의 목적은 RED를 만드는 것이 아니라, 아직 보장되지 않은 행동을 계약으로 만드는 것이다.**

현재 코드가 이미 계약을 만족한다면 실패를 인위적으로 만들지 않는다.

또한 Debug는 문제를 설명하기 위한 도구이지, Debug 자체가 별도 시스템으로 커져서는 안 된다.

## 캐릭터 Pushbox까지 이어진 발견

바위를 확인하던 Debug 화면에서 캐릭터의 Pushbox도 다시 보게 되었다.

처음에는 캐릭터 Pushbox가 너무 크다고 생각했지만 실제 코드 확인 결과는 달랐다.

```text
Player          16×16 sprite / Pushbox 8×8
Melee Goblin    16×16 sprite / Pushbox 6×6
CrossbowGoblin  16×16 sprite / Pushbox 6×6
```

크기는 이미 충분히 작았다. 실제 문제는 "크기를 더 줄여야 하는가"가 아니라 **Sprite 안에서 Pushbox가 어디에 위치해야 자연스러운가**였다.

이 과정에서도 같은 원칙이 다시 확인되었다.

```text
Sprite bounds
≠ Pushbox bounds
≠ Hurtbox bounds
≠ Hitbox bounds
```

각 영역은 서로 다른 의미를 가진다.

- Sprite: 보이는 전체 캐릭터
- Pushbox: 이동 시 실제로 자리를 차지하는 몸통
- Hurtbox: 공격받는 영역
- Hitbox: 공격하는 영역

숫자를 통일하는 것보다 각 의미에 맞게 정의하는 것이 중요했다.

## 최종적으로 얻은 설계 원칙

### 1. Grid와 Object Collision을 구분한다

```text
StageData BLOCKED
→ 큰 지형 / 경계 / 벽

Static Obstacle
→ 개별 오브젝트
```

작은 오브젝트를 무조건 grid BLOCKED로 표현하지 않는다.

### 2. 보이는 크기와 충돌 크기를 분리한다

```text
Visual footprint != Collision footprint
```

시각적 실루엣 전체를 충돌 영역으로 사용하면 둥근 오브젝트와 캐릭터에서 불필요한 걸림이 생길 수 있다.

### 3. 충돌 시작과 충돌 후 이동을 분리해서 생각한다

```text
Collision size
→ 언제 부딪히는가

Movement resolver
→ 부딪힌 뒤 어떻게 움직이는가
```

한쪽을 조정해서 다른 문제까지 해결하려 하지 않는다.

### 4. 플레이 감각은 사람이 확인하고, 재현 가능한 규칙은 테스트로 고정한다

mGBA 플레이는 최종 인수 테스트다.

TDD는 그 과정에서 발견된 구체적인 규칙을 다시 깨지지 않게 고정하는 역할을 한다.

### 5. 실제 코드를 먼저 확인한다

지시서의 숫자나 이전 가정이 현재 코드와 다르면 작업을 멈추는 것으로 끝내지 않는다.

```text
현재 코드 확인
→ 원래 사용자 목표를 다시 해석
→ 현재 상태에서 필요한 최소 변경 탐색
```

이 순서가 중요하다.

## 앞으로의 적용

이 경험은 Stage2에서도 그대로 적용할 수 있다.

다리, 벽, 기둥, 계단처럼 시각 구조와 이동 구조가 달라지는 요소를 추가할 때도 "그림의 타일"과 "게임 플레이 의미"를 한 구조에 억지로 묶지 않는다.

특히 앞으로 2층 전장을 구현할 때도 다음 구분을 유지한다.

```text
Visual Layer
Movement Layer
Collision / Push
Combat Hit/Hurt
Trigger / Stage progression
```

Stage1의 작은 바위 하나를 자연스럽게 통과시키는 문제에서 시작했지만, 결과적으로 이 프로젝트에서 **보이는 것과 게임 규칙을 분리하는 방법**을 배운 작업이었다.
