# Repository 작업 Workflow

이 문서는 `AGENTS.md`의 핵심 규칙을 실제 작업 절차로 풀어쓴다. `AGENTS.md`는 항상 읽는 진입점이고, 이 문서는 분석·승인·브랜치·검증·커밋·문서 갱신 절차가 필요한 작업에서 따른다.

## 1. 기본 작업 흐름

기본 흐름은 다음과 같다.

```text
Repository 조사
→ 확인된 사실 / 설계 판단 / 미확인 사항 구분
→ 작업 계획 또는 분석
→ 필요한 경우 사용자 승인
→ 작업 브랜치에서 변경
→ 검증
→ diff 검토
→ 커밋
→ 결과 보고
→ 사용자 지시에 따라 main 반영
→ Decision / Journal 갱신 필요성 검토
```

승인 게이트가 없는 단순 변경은 사용자의 지시 범위 안에서 바로 진행할 수 있다.

사용자가 `확인 후 진행`, `먼저 검토`, `보고 후 수정`처럼 결과를 먼저 확인하겠다고 지시한 경우에는 아래 승인 게이트를 최우선으로 적용한다.

## 2. 사용자 승인 게이트

- 사용자가 분석, 검토 또는 제안 결과를 먼저 확인한 뒤 진행하도록 지시한 작업은 분석 단계와 Repository 변경 단계를 분리한다.
- 중간 보고, 분석 결과 공유, 추천안 제시는 사용자 승인으로 간주하지 않는다.
- 사용자가 `진행`, `반영`, `수정`, `커밋` 등 Repository 변경을 허용하는 명시적인 의사를 표시한 뒤에만 파일 수정·생성·삭제를 수행한다.
- 승인 전에 코드나 문서를 미리 수정한 뒤 `merge하지 않았으므로 괜찮다`고 해석하지 않는다.
- 승인 전에는 분석만 수행한다.
- 승인 후 Repository 변경을 수행한다.

핵심 원칙:

```text
승인 전에는 분석만.
승인 후에 수정.
수정은 작업 브랜치에서.
```

## 3. 브랜치 작업 원칙

- Repository 변경이 필요한 작업은 기본적으로 최신 `main`을 기준으로 작업 브랜치를 생성한다.
- `main` 직접 수정은 기본값이 아니다.
- 기능, 버그 수정, 구조 변경, 문서 정책 변경은 작업 브랜치 사용을 기본으로 한다.
- 사용자가 명시적으로 `main에 바로 반영`을 요청한 경우에만 브랜치 절차를 생략할 수 있다.
- 하위 에이전트는 브랜치 생성, commit, push, merge를 임의로 수행하지 않는다.
- 최종 commit은 주 에이전트가 담당한다.
- `main` merge는 사용자 지시 또는 프로젝트의 명확한 기존 승인 절차에 따른다.

작업 브랜치에서는 다음 흐름을 따른다.

```text
변경
→ 검증
→ diff 확인
→ commit
→ 결과 보고
```

사용자가 작업 전에 별도의 승인 게이트를 요구했다면 승인 전에는 변경하지 않는다.

## 4. Repository Grounding

설계와 구현 작업에서는 다음을 구분한다.

### 확인된 사실

실제 코드, Git, Issue, PR, 문서에서 확인한 사항.

### 설계 판단

확인된 사실을 바탕으로 AI가 제안하거나 해석한 사항.

### 미확인 사항

아직 확인하지 않았거나 추가 조사가 필요한 사항.

확인되지 않은 내용을 현재 프로젝트의 사실처럼 작성하지 않는다.

코드는 현재 동작의 1차 근거다. 문서와 코드가 충돌하면 문서를 기준으로 즉시 코드를 수정하지 않고 실제 구현, Git history와 기존 Decision을 먼저 조사한다.

## 5. 멀티 에이전트 사용

멀티 에이전트는 다음 조건에서만 사용한다.

- 독립적인 조사 또는 검증 영역이 두 개 이상 존재한다.
- 담당 파일이나 책임 영역을 겹치지 않게 나눌 수 있다.
- 병렬 작업의 이득이 통합 비용보다 크다.
- 별도 구현자 또는 검토자가 오류 방지에 실질적으로 도움이 된다.

다음 작업에는 사용하지 않는다.

- 한 파일의 단순 수정
- 짧은 문서 변경
- 순차 의존성이 높은 작업
- 같은 파일을 여러 에이전트가 수정해야 하는 작업

주 에이전트는 목표 정리, 작업 분해, 담당 지정, 결과 검토, 통합, 최종 검증과 commit을 책임진다. 하위 에이전트 결과를 검증 없이 적용하지 않는다.

## 6. Decision 관리

`docs/decisions/`는 중요한 설계 선택과 이유를 기록한다.

기존 Decision과 충돌하는 변경이 필요하면 다음 순서로 진행한다.

1. 기존 결정을 확인한다.
2. 기존 결정 이유를 확인한다.
3. 현재 문제가 된 이유를 설명한다.
4. 유지안과 변경안을 비교한다.
5. 사용자에게 보고한다.
6. 사용자 승인을 받는다.
7. 새 Decision으로 변경 이유를 기록한다.

기존 Decision을 현재 결론에 맞게 덮어써서 역사를 지우지 않는다.

## 7. Journal 관리

`docs/journal/`은 작업 일지가 아니다.

다음과 같은 경우에만 Journal 후보로 판단한다.

- 처음 생각과 실제 결과가 달랐음
- 중요한 설계 판단이 변경됨
- 실패에서 의미 있는 교훈을 얻음
- 중요한 대안을 비교하고 선택함
- 향후 책에 남길 가치가 있음

단순 commit/PR 내용을 반복하지 않는다.

AI는 Journal 필요성을 판단하여 초안을 제안할 수 있다. 사용자가 검토 또는 승인한 뒤 반영한다.

Journal 전체를 모든 작업의 기본 컨텍스트로 사용하지 않는다. 과거 판단의 이유가 필요할 때 관련 Journal만 선택적으로 확인한다.

## 8. 검증

변경 유형에 맞는 검증을 수행한다.

코드 또는 빌드 대상 자산 변경 시:

- 가능한 경우 `make -j2`
- 필요하면 `make clean` 후 `make -j2`

모든 변경에서:

- 가능한 환경에서는 `git diff --check`
- 요청 범위 밖 변경 확인
- 기존 사용자 변경 보호
- 기존 실패와 신규 실패 구분

실행하지 않은 검증을 성공했다고 보고하지 않는다.

문서만 변경한 작업에서는 불필요한 ROM 빌드를 의무적으로 수행하지 않는다.

## 9. 완료 보고

다음을 간결하게 보고한다.

- 작업 브랜치
- 변경 파일
- 확정한 규칙 또는 구현 내용
- 실행한 검증과 결과
- 실행하지 못한 검증
- 남은 위험
- Decision/Journal 갱신 여부
- commit SHA
- main 반영 여부

`작업 브랜치에 commit됨`과 `main에 merge됨`을 명확하게 구분한다.
